# ADR: выбор стека

Решения относятся к профилю сдачи. [Архитектура](architecture.md) показывает границы, [нагрузочный отчёт](load-report.md) — что реально проверено.

## ADR-001. Закрытый контур

**Решение:** `APP_MODE=airgap`, локальные модели, предварительно загруженный корпус, offline-флаги и запрет egress. Внешние API не участвуют в сдаче. **Trade-off:** меньше актуальность корпуса, зато автономность и контроль данных; импорт выполняет оператор. Исходный connected-режим оставлен для разработки.

## ADR-002. Stateful agent

**Решение:** LangGraph и PostgreSQL checkpoint; plan → retrieve → analyze → review → повтор/завершение, с бюджетом и lease. **Trade-off:** явное состояние сложнее линейного скрипта, но поддерживает повторный поиск, уточнение и восстановление. Свободная multi-agent оркестрация не нужна MVP. [Код](../backend/research.py).

## ADR-003. GraphRAG

**Решение:** FTS + Qdrant + граф Document/Chunk/Identifier, RRF и rerank. Граф хранится в PostgreSQL и извлекается детерминированно из технических идентификаторов. **Trade-off:** проще восстановление и ACL, чем отдельный Neo4j с LLM-онтологией; ниже семантическая полнота. Польза качества требует размеченного A/B. [Код](../backend/knowledge_graph.py).

## ADR-004. Self-hosted данные

**Решение:** PostgreSQL для прав/очереди/графа, Qdrant для векторов, том для оригиналов. **Trade-off:** Qdrant проще для одного индекса MVP, чем кластер Milvus; один индекс с обязательным фильтром UUID проще коллекций на пользователя. Индекс можно пересоздать из версий документов.

## ADR-005. Serving и квантование

**Решение:** vLLM 0.30.0; на A100 измерен Qwen3.8-27B BF16, context 8192, prefix caching, GPU memory utilization 0.90. Embedding/reranker — локальные Qwen3 0.6B; reranker использует обученные yes/no logits. **Trade-off:** BF16 помещается на 80 GB; для меньшей GPU предусмотрен [AWQ-профиль](../infra/compose.consumer-gpu.yaml), но он не измерен. GGUF потребовал бы отдельного serving-профиля; SGLang/TGI не сравнивались нагрузкой. Версии весов/image digest зафиксированы в raw evidence.

## ADR-006. Сложные PDF

**Решение:** Docling для структуры/таблиц, Tesseract rus+eng для OCR, локальный VLM для отдельного анализа изображений. **Trade-off:** pypdf не распознаёт сканы; VLM на каждой странице дороже и может ошибаться в геометрии. Веса Docling доставляются заранее, инженерные размеры проверяет человек.

## ADR-007. Security-by-Design

**Решение:** доменные роли + ACL чанков, фильтрация до retrieval/graph traversal и повторный контроль перед текстом, цитатами и экспортом. Источник не получает полномочий через prompt. **Trade-off:** SQL-список разрешённых ID прост для MVP, но требует пересмотра на большом корпусе. PII-фильтр email/телефонов ограничен; это не DLP. [Код](../backend/access.py).

## ADR-008. Наблюдаемость и секреты

**Решение:** OTel → Jaeger; Prometheus/Grafana и self-hosted Langfuse — дополнительные infra-профили. Атрибуты без промптов/ответов/секретов. OpenBao с TLS предусмотрен `security-prod`; измеренный стенд использует `.env` 0600. **Trade-off:** Jaeger проще для demo, Langfuse добавляет зависимости; ни наличие конфигурации, ни trace не доказывают промышленную готовность.

## ADR-009. Импорт корпуса

**Решение:** оригиналы, версии и SHA-256; публичные пакеты переносятся оператором, суммы сверяются перед индексированием. **Trade-off:** ручной импорт менее удобен web search, но соответствует закрытому контуру. SHA-256 проверяет целостность, а не подлинность отправителя.

## ADR-010. Проверяемый отчёт

**Решение:** Markdown — источник, PDF — представление после повторного ACL. Механическая проверка цитат/чисел и LLM-проверка утверждений; неподтверждённый текст удаляется. **Trade-off:** можно потерять полезную формулировку/OCR-формулу, зато неподтверждённый ответ не считается успешным. PDF через ReportLab/MathText не исполняет модельный TeX. [Код](../backend/report_review.py).
